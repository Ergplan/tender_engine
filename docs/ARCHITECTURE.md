# Architecture

Kept current in the same commit as the code that changes it. Sources of authority: the invariants and locked decisions in `CLAUDE.md`, the inheritance choices in `docs/INHERITANCE.md`, dated decisions in `docs/DECISIONS.md`.

## Components

```mermaid
flowchart LR
  R[Reviewer browser: review link] -- "443 (TLS, internal CA)" --> C[caddy]
  U[Signed-in user: Google OIDC session] -- 443 --> C
  P[API client: tie_live key] -- 443 --> C
  H[MCP host: Claude, an IDE; OAuth access token] -- "443 /mcp" --> C
  C -- "/" --> W[web: React + Vite]
  C -- "/api/*, /mcp, /health (marked public)" --> A[api: FastAPI, routes only; auth middleware resolves the principal; the MCP server mounted at /mcp]
  C -- "/files/* after asking the API" --> V
  A --> D[(db: PostgreSQL 16)]
  K[worker: job poller] --> D
  A --> V[/data volume/]
  K --> V
  K -- "core/llm only" --> L[Claude Fable 5.1]
  G[agent: agent_pass jobs] --> D
  G --> V
  G -- "core/llm only" --> O[OpenAI, Agents SDK]
  T[tests: watcher] --> D
  T -. writes .-> S[.ci/status.json]
```

| Service | Image | Command | Notes |
| --- | --- | --- | --- |
| `db` | `postgres:16` | default | databases `tender` (app) and `tender_ci` (watcher and pytest) |
| `api` | `infra/docker/Dockerfile.python` (target `app`) | `uvicorn api.main:create_app --factory` | routes only; no business logic, no LLM calls |
| `worker` | same image | `python -m worker.main` | one process; polls `job` every 2 s and runs the parse → section map → extract → validate chain; claims only the job kinds it has handlers for |
| `agent` | same image | `python -m agent.main` | the independent agent pass (Stage 5A): one process that claims only `agent_pass` jobs and runs the OpenAI Agents SDK loop, every model call logged through `core/llm/agent_calls.py` |
| `web` | `infra/docker/Dockerfile.web` | Vite dev server | the reviewer screen; calls `/api/v1/*` through `web/src/api/` only |
| `caddy` | `caddy:2` | `infra/Caddyfile` (routes in `infra/Caddyfile.routes`) | TLS with Caddy's internal CA on the static IP; marks API requests as public; serves stored files from `/data` (read-only mount) after `forward_auth` to the API |
| `api-e2e`, `caddy-e2e`, `playwright` | tests image, `caddy:2`, `mcr.microsoft.com/playwright` | compose profile `e2e`, started only by `make test-ui` | the browser tests: an API on database `tender_e2e` seeded by `tests/e2e/seed_review.py` with a scripted model, the same proxy routes over HTTP, and Playwright |
| `tests` | `infra/docker/Dockerfile.python` (target `tests`: dev dependencies plus Node) | `python infra/ci/run_checks.py --watch` | the continuous test pipeline |

## Data model

| Table | Purpose | Who writes it | Stage |
| --- | --- | --- | --- |
| `tenant` | one row per tenant; `ergplan` seeded by migration 0001; `plan` (migration 0017: `enterprise`, `free`, `public`) and the reserved `public` library tenant seeded for Stage 5D. No `tenant_id` of its own, so no row-level policy | migration only; from Stage 5D, sign-up | 0B, 5C |
| `llm_call_log` | one row per LLM call: prompt name and version, model, input hash, output, tokens (`tokens_in` is the uncached input; `cache_write_tokens` and `cache_read_tokens` are the rest of it), `mode` (`sync` or `batch`), `batch_id`, `cost_usd` with the cache and batch factors applied, latency, status, request id, `extraction_run_id`; `agent_run_id` (migration 0016) for a turn of the agent pass | `core.llm.client.LLMClient` only (`call`, and `collect_batch` for calls read from a batch); `core.llm.agent_calls.LoggedModel` for the agent's turns | 0B, 1, 3, 5A |
| `llm_batch` | a batch handed to the provider's batch API: provider batch id, run, wave (1 writes shared windows to the cache, 2 reads them), status `submitted/collected`, the custom id and input hash of each call | `LLMClient.submit_batch`; status by `collect_batch` | 3 |
| `document` | an uploaded PDF: sha256 (unique per tenant), filename, mime, page_count, storage_path, status `uploaded/parsed/failed`, error; provenance `source_url` and `retrieved_on` (migration 0013, nullable; a later upload of the same file fills them where blank, never overwrites) | `IngestService.upload`; status and page_count by `ParseService.parse` | 1 |
| `page` | per page: text, width and height in PDF points, `render_path` (PNG at 150 dpi), `char_boxes` (one `[x0, top, x1, bottom]` per character of `text`, null for layout whitespace), `has_text_layer` | `ParseService.parse` | 1 |

**Row-level security (Stage 5C, migration 0018).** Every table with a `tenant_id` has `ENABLE` and `FORCE ROW LEVEL SECURITY` and its policies (four; the tenant registry two): a row is read when `tenant_id` equals the session setting `app.tenant_id` or is in the comma list `app.read_tenants`, and inserted, updated or deleted only when it equals `app.tenant_id`; the scope `*` (`core.db.SYSTEM_TENANT`) passes every policy and is set only by the identity steps that must look across tenants before a tenant is known (a login, a review link, an API key). `core.db` sets both settings with `set_config(…, true)` at the start of every transaction from `session.info` (`make_session_factory(engine, tenant_id, read_tenants=…)`; `set_tenant` for a session already made); a session with no tenant sees nothing. A superuser bypasses row-level security whatever `FORCE` says, and the compose database's owner `tender` is one, so the app connects as `tender_app`, a role created by the migration with no ownership (`DATABASE_URL`); migrations and the test clean-up run as the owner (`MIGRATION_DATABASE_URL`, `TEST_DATABASE_URL` against `TEST_APP_DATABASE_URL`). `tests/core/test_rls.py` reads across with no tenant filter and gets zero rows, and sees the database refuse a write into another tenant and into `public`.

Invariants the database itself enforces (migration 0002): a `candidate` row can be neither deleted nor updated in any column but `status`; `evidence_span` and `audit_log` rows can be neither updated nor deleted. Tests in `tests/core/test_invariants.py` try each and expect the refusal.

A candidate, approval and canonical fact belong to an **object** (`object_type`, `object_id`, `object_version`). In Stage 1 the object is the document itself (`object_type = "document"`, version 1). Stage 2 passes `tender` and the tender version number, which is how a canonical fact becomes attached to a tender version without core knowing what a tender is.

See "Independent agent pass (Stage 5A)".

Stage 5C adds no step and no writer: `ApprovalService.approve` remains the only writer of `canonical_fact`. The published view (`tender/services/published.py`, `GET /tenders/{id}/published`) reads `canonical_fact` and nothing else — never a candidate — and the identity tables sit beside the pipeline, not in it.

Stage 6 adds the deterministic import step above and no writer: an imported row is a candidate, approved by a reviewer against the PDF like a model's reading, and `ApprovalService.approve` remains the only writer of `canonical_fact`.

Stage 5D adds no step and no writer either. A correction case (`correction_case`, `POST /public/corrections`) never changes a value: it opens a review round scoped to the field, and a reviewer's new approval, through `ApprovalService.approve`, is the only thing that can change what is published; the change then shows in `list_changes` with its date and reason. The MCP tools read the published view, the changelog and the comparison — `canonical_fact` through the same services — and write only a user's own rows (assumptions, watchlist) in the user's own tenant. The financial engine (`tender/services/finance.py`) reads tender-fixed parameters from the published view and the user's assumptions from `model_assumption`; its figures are computed, never stored as facts.

Candidate outcomes that never reach a reviewer as a value: `not_found` (the model returned null; shown as "no value"; it becomes `needs_review` with `required_present` failed when the field is required; it can be decided as not_in_document, or as edited when the reviewer supplies located evidence) and `rejected` (a value came with no quote; stored for the record, never shown, cannot be approved).

A schema is data handed to core: `core.schemas.ExtractionSchema` (field groups with routing hints, fields with value type, unit, range and regex) registered in a `SchemaRegistry` together with any cross-field rules. Core names no tender field. In Stage 1 the deployed API and worker start with an empty registry; the tender schemas are registered in Stage 2. Tests register a small contract schema and, for the end-to-end run, a 12-field FDRE schema (`tests/fixtures/`).

The LLM boundary is `core/llm/`: `core.llm.client.LLMClient.call(LLMRequest) -> LLMResponse` loads a registered prompt version through `core.llm.registry.load_prompt`, calls the model with a Pydantic output schema, and writes `llm_call_log` for every outcome including failures. Nothing else in the codebase may call the Anthropic SDK. From Stage 5A the boundary has a second door for the other model family: `core.llm.agent_calls.LoggedModel` wraps the OpenAI Agents SDK's model so that every turn of the agent pass writes an `llm_call_log` row (prompt `agent_pass/v1`, the OpenAI model, input hash, output items, tokens with the cached part told apart, cost at the configured list prices, latency, status); nothing else in the codebase may call OpenAI. Prompts: `core/llm/prompts/section_map/v1.md`, `core/llm/prompts/extract/v1.md` and `extract/v2.md` (2026-10-15: the withdrawal rule — a provision the attached pages remove is returned as `withdrawn: true` with value null and the removing words as evidence, never inferred from silence and never for a value that merely changed; `build_group_model` adds `withdrawn`, default false, to every field answer).

### Cost of extraction (Stage 3)

Native PDF pages cost about 2,800 input tokens each, and in Stage 2 every field group sent its own pages. Two things reduce that, both inside `core/llm/` and `core/services/extract.py`:

- **Shared windows as a cached prefix.** `share_windows` takes each group's window and merges windows step by step, always the two whose union makes their groups read the fewest extra pages, and keeps the cheapest partition it passes. The cost of a window is counted in uncached pages: one group pays every page in full; several pay one cache write (1.25 times the input price, 2 times for the one-hour cache of a batch run) and a cache read (0.025 times) for each further group; every call also costs its output, weighed as 6 pages. A merged window is the union of its groups' pages and never exceeds the 80-page cap of a group. A call on a shared window marks its PDF with `cache_control`; everything before that mark must be the same for the calls that share it, so the system prompt is the text all section prompts inherit (`extract/v1`, `Prompt.shared_text`) and the section's own text (`Prompt.own_text`) follows the document. The prompt files are unchanged. The output schema is part of the prefix too, so the calls on a shared window all send one schema that fits any group (`SharedAnswer`: a list of entries with key, value, confidence, rationale and evidence); `typed_answer` then checks the answer against the group's own typed model (every field present once, values of the right kind), and a call whose answer does not pass is made again on its own with the typed model. A window that is not shared is sent exactly as in Stage 2, typed model included. Calls are made window by window, chunk by chunk, and group by group within a chunk, so the readers follow the writer while the entry is alive. The same pages always give the same PDF bytes (`_sub_pdf` writes no fresh file id).
- **Batch API.** A run has a `mode`. `batch` is for runs nobody waits for (`python -m scripts.ingest_tenders extract`, and `"mode": "batch"` on `POST /tenders/{id}/extract`); `sync` stays the default of the API. A batch run goes through `ExtractService._batches_done`: wave 1 holds the call that writes each shared chunk to the cache and every call on an unshared window; wave 2, sent when wave 1 has ended, holds the calls that read. The extract job does not wait: it queues another `extract` job `llm_batch_poll_seconds` later and returns. `LLMClient.collect_batch` writes the same `llm_call_log` row per call as a direct call. A call that failed inside a batch is then made directly.
- **An answered call is not paid for again.** `LLMClient.logged` returns the answer of an identical call (same model, prompt, schema and content, by input hash) already logged for the run. Extraction asks it before every call, which is how the results of a batch are read and how an interrupted run resumes.

`core.llm.pricing.call_cost` computes `llm_call_log.cost_usd`; run costs and the extraction summary are sums of it.

### Review tokens and what a request may reach (Stage 3)

`api/middleware/review_token.py` runs on every `/api/v1/` request.

- A request with a review token (header `X-Review-Token`, or the cookie `review_token` for the page images and the PDF the browser fetches itself) is that token's reviewer (`request.state.review`; `api.deps.get_reviewer` returns the token's reviewer name, whatever `X-Reviewer` says). It may call only the routes in `ALLOWED`: the review session, its own tender (`/tenders/{id}` with `versions`, `review`, `review-state`, `view`, `snapshot`, `complete-review`), the schema, the documents of that tender (`pages`, `sections`, `search`, page render), `POST /approvals` and `files-auth`. Another tender or one of its documents is 404; any other route is 403. `ApprovalService.approve` is given the token's tender as `object_scope`, so a candidate of another tender is not found.
- An unknown token is 401, a revoked or expired one 410, each with a plain sentence the screen shows as it is. A completed review can be read and not changed: every non-GET request is 409.
- A request that came through the public proxy (Caddy adds `X-Public-Request`, which a client cannot remove) and carries no token is 401, whatever it asks for, except `/health`. Port 443 is open to the world, so this is what stands between the internet and the API.
- A request made inside the deployment (management commands, tests, `docker compose exec`) carries neither and is not limited; it names its reviewer in `X-Reviewer`. `POST /review-tokens`, tender creation, uploads and extraction are reachable only this way.

`api/middleware/audit.py` writes one `audit_log` row (`table_name = "request"`) for every non-GET request under `/api/v1/`: the actor, the path, the status it ended with and the token id. Stored files (`/files/documents/<sha>.pdf`, `/files/renders/<sha>/<n>.png`) are served by Caddy from `/data`, with range requests and a one-day private cache, after `forward_auth` to `GET /api/v1/files-auth`, which checks that the file belongs to a document of the token's tender.

Since Stage 6 a review token belongs to an object, (`object_type`, `object_id`): a tender, or an award. `ReviewContext.scope` is what the middleware checks a route's `{tender}` or `{award}` against, `tender.services.tokens.document_belongs` what a `{document}` or a stored file must belong to (a document of any version of the tender, or the award's publication), for the middleware, `/files-auth` and `GET /files/*` alike. The award token reaches `GET /awards/{award}`, `/review`, `/review-state`, `/results`, `POST /awards/{award}/complete-review`, the document routes of its publication and `POST /approvals`; nothing of any tender.

### The reviewer's view of a tender (Stage 3)

`tender.services.review.tender_review` (`GET /tenders/{id}/review`) is the read model of the reviewer screen. Core's review state is per object version; here every field appears once, with one entry per version that says something about it: the original always, a later version only where it gives a value (or has been decided). The entry to decide (`current`) is the latest one the reviewer has not set aside as "not in document", so what is reviewed is the tender's current value, tagged with its version; setting an amendment's entry aside brings the earlier one back. A field is decided when its current entry is approved, edited or not in document; a flag does not count. `can_complete` is true once no required field is undecided.

**A review round (2026-10-15).** A link whose token carries `from_version` opens a round: `tender_review(..., round_no, from_version)` marks in scope the fields a version from `from_version` on states, the summary (written from every field) and any derived table whose rule reads an in-scope field (`ReviewField.in_scope`), and counts `decided`, `total`, `required_undecided` and `can_complete` over the scope only; `TenderReview.round` gives the round number, the opening version, and how many fields are in scope and carried. A carried field keeps its entries and, where it has one, its decision, with the reviewer, time and version it was decided on; one without a decision is shown undecided and does not hold the round back. `GET /tenders/{id}/review` reads the round from the request's token (a request without a token sees the whole tender); `GET /review-session` says `round_no` and `from_version`. On screen, a carried field is a compact `CarriedCard` with its provenance line and a "Review again" control that opens the ordinary card; the section list counts over the scope and names the carried; the header banner says which version opened the round and what is left; the keys skip carried rows; the completion control reads "Complete round N".

`complete_review` (`POST /tenders/{id}/complete-review`, with the review token) refuses while a required field is undecided, then sets `review_token.completed_at` and `tender.status = reviewed`, stores `current_view` as a `tender_review_snapshot`, and audits it. It writes no canonical fact.

A decision carries the active decision the reviewer last saw (`previous_approval_id`, null for none); when the field has been decided again since, `ApprovalService.approve` raises `StaleDecisionError` and the API answers 409.

**Clearing a decision** (2026-10-06). The decision `cleared` supersedes the active decision on a field and leaves the field undecided: an approval row like any other, audited, with no canonical fact and no feedback row (the earlier decision's feedback row stays as history; a feedback report must count only feedback of active approvals). A cleared field reads as undecided and can be decided again. On the screen: "Clear decision" on a decided or flagged card, key `U`. There is no delete: nothing a reviewer did disappears.

**Second readings** (2026-10-06). A field can have more than one reviewable candidate: a section read in two page windows, or read again in a later pass. `ReviewStateService.for_object` returns, per field, the reading it shows and `alternatives`: every other reviewable candidate whose value, typed as it would be stored, differs from it. Readings that agree are not listed. The reading a reviewer has decided on is the one shown, whichever it came from; otherwise the best-evidenced one. The card draws each alternative with its value, confidence and evidence chips and offers "Use this reading", which approves that candidate; the field's active decision is superseded as with any other decision. That two readings differ is kept as a signal: it marks a field the document states ambiguously.

## Tender domain layer (Stage 2)

`tender/` sits on top of `core/` and core does not import it (a test enforces this). What the tender layer adds is data (schemas, prompts), deterministic rules, and the tender, version and document tables.

**Domain packs.** `tender/domain_packs/core/common.yaml` holds the fields every tender has (`core.<section>.<field>`); `tender/domain_packs/power/pack.yaml` holds the power fields every power tender shares (`sector.power.common.<field>`); one YAML per tender type holds its own (`sector.power.<type>.<field>`) and lists the common sections it includes. `tender.services.packs.load_catalog` compiles each type into a core `ExtractionSchema` named `tender.<type>` `v1`, once, at start-up, and `Catalog.register` hands the schemas, the tender value types, the cross-field rules and the run rules to core's `SchemaRegistry`. A type resolves to one pack. A combined type is its own YAML with `inherits: [a, b]`, folded in at compile time; two different definitions of one field or section are an error. A malformed file (unknown key, unknown section or role, a path outside the pack's namespace) is refused.

**Sections.** A section is what the reviewer sees as one block and what the extractor reads in one call: summary, identity_and_scope, key_dates, eligibility, guarantees, commercial, penalties, connectivity_and_compliance, documents, then one type section (solar_tech, wind_tech, hybrid_mix, fdre_profile, bess_performance, tbcb_elements, gen_tech, epc_scope, ipp_model_inputs). Each has a prompt (`summary` or `extract/<section>`), the document roles it is read from, and routing hints. Every section prompt has the header `extends: extract/vN`: its text is core's extract prompt followed by the domain guidance, and its hash covers both. Since 2026-10-15 every section's latest prompt extends `extract/v2` (core: commercial v4, documents v2, eligibility v2, guarantees v3, identity_and_scope v2, key_dates v2, penalties v4; power: bess_performance v3, connectivity_and_compliance v2, epc_scope v3, fdre_profile v3, gen_tech v2, hybrid_mix v3, ipp_model_inputs v2, re_rtc_profile v2, solar_tech v3, supply_sources v2, tbcb_elements v3, wind_tech v3), the pack YAMLs pin those versions, and a run asks for `v2` by default (`TenderService.start_extraction`, the API, the extraction runs an amendment map starts; the map's own prompt stays `amendment_map/v1`, `MAP_PROMPT_VERSION`). Candidates read earlier keep their versions; nothing was read again except on request.

**Versions and documents.** The original documents of a tender are version 1; each corrigendum, amendment or clarification is a new version (`TenderService.add_version`). Further documents of a version (PPA, PSA, technical volume) are attached with `attach_document`. Candidates, approvals and canonical facts of a tender carry `object_type = "tender"`, `object_id = tender.id`, `object_version = version_no`.

**Extraction of a version** (`TenderService.start_extraction`, planned by `tender.services.versioning.plan_groups`): one core extraction run per document, limited to the groups that document is read for. Version 1: the groups whose roles include the document's role (an RfS is read for every section; a PPA or CfDA for commercial and penalties; a technical volume for the type section). A later version: only the groups whose routing keywords occur in the document's text, never the summary. Fields a later version does not mention get no candidate in that version and keep the earlier canonical facts.

**Current view** (`tender.services.current_view.current_view`): per field, the current canonical fact of the latest version that states a value or withdraws the provision, with that version's number and kind. A later version that has no value for a field, or whose reviewer marked it not in document, leaves the earlier fact in place; a fact with `withdrawn` replaces it, and the view then holds no value but says so (`FieldView.withdrawn`, `withdrawn_value` — what the earlier fact held — and `withdrawn_from_version`), so a ceiling that never existed is told apart from one an amendment removed. Canonical facts only, never candidates.

**Rules** (plain Python, no model; a failed rule is an error unless its outcome is marked a warning, which is shown but does not send the candidate to review): `date_order` (queries closing before the pre-bid meeting is a warning), `emd_pbg_within_10x` (core pack); `bid_capacity_order`, `elements_have_kv` (power pack); ranges in the YAML (tariff ceiling 1 to 15 INR/kWh, PPA tenure 10 to 35 years, SCOD at least 1 month); type rules as required fields (fdre: demand profile and availability shortfall penalty; bess: MWh and cycles per day; transmission: elements; hybrid: minimum share per resource); and the corrigendum rule `later_version_evidence`, a run rule: a value produced for a later version must carry evidence from a document of that version.

**Required fields** are required of the tender, not of each version or document: an empty candidate passes `required_present` when another run of the same or an earlier version has a value, and the tender review state lists `missing_required`.

**Values with a basis.** Bid validity carries its unit (days or months), financial closure its reference (forward from a date, or back from SCOD), turnover and liquidity whether they are absolute or per MW; the number is stored as printed.

**Amendment routing.** `TenderService.start_extraction` does not start a run for an amending document; it queues the job `amendment_plan`. `tender.services.amendment_map.AmendmentMapper.plan` computes the keyword sections, maps the whole document against the schema's sections with one text call (`amendment_map/v1`), writes the comparison to the audit log (`amendment_routing`) and starts the run for the union.

**Notices.** `scripts/fetch_notices.py` files the agency's published notice page as a `nit` document on the tender's latest version.

**Formulas and deferred dates.** EMD and PBG have a per-MW field and a formula field (`core.guarantees.emd_formula`, `pbg_formula`), each with its own evidence; the per-MW field is filled only where the tender states one figure. Dates the document defers to the NIT or a later notice stay null, and `core.key_dates.dates_deferred_note` records which dates are deferred and to which document, with the deferral quoted.

**Core extension points added for this stage** (each with a test, each in DECISIONS.md): a run may be limited to named groups (`extraction_run.groups`); candidates are superseded per field and per document, so the documents of one version do not supersede each other; review state reads across the runs of a version; run rules (`SchemaRegistry.register_run_rule`); prompt inheritance (`extends`); `FieldDef.item_keys` for record lists.

**Intended path, not built:** a second sector pack; automatic sector classification at ingestion; composition of several packs over one tender; packs as separately licensed products. The second sector is added when power is at measured reliability and a customer is attached to it, as a test of whether `core/` truly generalises. The financial model will take a model type, `model_tender(tender_id, model_type)`, with `power_project_finance` the only implementation; `epc_contract_cashflow`, `supply_contract_margin` and `o&m_contract_economics` are future work.

### Tender documents and roles (decided 2026-10-04)

A `tender_version` owns many documents through a link table, each with a role. This refines the Stage 2 prompt, which gave `tender_version` a single `document_id`.

| Table | Columns | Notes |
| --- | --- | --- |
| `tender_version` | tender_id, version_no, kind (original/corrigendum/amendment/clarification), issued_on, summary_of_change, supersedes_version_id | no `document_id` column |
| `tender_version_document` | tender_version_id, document_id, role | role is one of `rfs`, `amendment`, `clarification`, `ppa`, `psa`, `cfda`, `technical`, `contractual`, `nit` |

- The original version of a SECI tender typically holds the RfS plus its standard PPA and PSA (or CfDA). An EPC tender holds a contractual and a technical document. A corrigendum, amendment or clarification still creates a new version with its own document; it is never attached to an existing version.
- Extraction routes each field group to documents by role. Commercial-section fields (payment security, change in law, termination compensation) may be routed to the `ppa` document.
- Nothing changes in the evidence model: an `evidence_span` already names a document id, so a canonical fact shows which document, page and box it came from.
- The roles are the same vocabulary used in `/work/tenders/<type>/<slug>/manifest.yaml`.

### The summary: a second pass over the record (2026-10-05)

The summary (`core.summary.plain_english_summary`) is a reading of the record, not another reading of the document. `tender.services.summary.SummaryWriter.write` runs after extraction:

1. **When.** The worker calls `SummaryWriter.after_validation` each time it has validated a run (`worker.runner.Runner`, `on_validated`). Once no extraction run and no amendment map of the tender is queued or running, it queues the job `tender_summary`. `POST /tenders/{id}/summarize` and `python -m scripts.ingest_tenders summarize` queue it on request.
2. **Sources.** `field_sources` takes the tender as the reviewer sees it (`tender_review`): for every field but the summary, the entry to decide (the latest version that states the field), with the reviewer's value where they have approved or edited it. A field takes part only when it has a value and located evidence. `narrative_sources` adds the sentences of the summary that was read from the pages (prompt `summary/v2`, still made during extraction, from at most 40 pages), but only those under "What is procured", "Buyer and offtaker" and "Location": what no single field holds. Each source has an id (`F12`, `N2`) and brings its located evidence spans.
3. **The call.** One text-only call, prompt `summary_record/v1`: the list of sources, no document. The model returns eight paragraphs under fixed headings; every sentence lists the ids of the sources it rests on, and a topic the record does not hold says so in a sentence without sources.
4. **Evidence is inherited, not located.** `compose` checks the headings, drops ids that do not exist (noting them and capping the confidence at 0.3), numbers the sources' spans in order of first use and writes the numbers after each sentence (`[3][4]`). The candidate's evidence spans are copies of the fields' spans: same document, page, box, characters and quote, with `ordinal` as the number. A passage two sources share is one span.
5. **Stored as a candidate.** `ExtractService.record_candidate` inserts it (audited, refused without located evidence) in a run of `mode = "record"` on the latest version the record draws on, and the earlier summaries of the tender leave review (`ExtractService.supersede`, audited). Then the usual `validate` job. If the call fails or the answer cannot be used, nothing is stored and the earlier summary stays. The summary is not written again from an unchanged record (same input hash as the one in review).

The corrigendum rule (`later_version_evidence`) does not apply to a record run: a summary of the record as amended carries evidence from earlier versions by design.

6. **Decided after the fields** (`SummaryGuard`, a `DecisionGuard` handed to `ApprovalService` by `api.deps.get_approvals`; `SummaryWriter.state`, served as `summary` in `GET /tenders/{id}/review`). The summary cannot be approved, edited or set aside while another field with a candidate is undecided (422, "decide the other fields first"); it can be flagged. It cannot be approved unless it was written from the record as it stands, reviewer's decisions included: when a decision leaves no other field undecided and the record has changed, the summary is queued to be written again, and until it is there approval is refused. A decision on another field that changes the record after the summary was decided withdraws that decision: the summary is flagged in the reviewer's name with the reason. Approving a field as it stands does not change the record: values reach the model in the form an approval stores (`normalise`), dates in words and amounts also in lakh and crore.
7. **What the card shows.** The model's own note on the summary (what it left out) is the first paragraph of the stored rationale and is shown above the text; the list of which number is which field follows it in the record and is not shown. Each inherited span carries `source`, the label of the field it comes from (migration 0011), which the screen shows with the quote when a number is pointed at or clicked. There is no list of chips on a text that carries numbers.

A section may pin its own prompt version and page cap (`prompt_version`, `max_pages` in the pack YAML, `FieldGroup`), which is how the page-read summary runs at `v2` in one call whatever version the run asks for. The page-read summary is made from the base documents only (`tender.services.versioning.plan_groups`).

### Derived tables: a third pass, over decisions, without a model (2026-10-08)

A section marked `derived: true` in a pack YAML (`SectionDef.derived`, `FieldGroup.derived`, `CompiledSection.derived`) is never read from pages: `ExtractService.start_run` refuses it as a group, `_run_groups` leaves it out, `versioning.groups_for_role` never plans it, and the trace, the extraction summary and the summary pass know it is no reading. Its fields are written by `tender.services.derive.DerivedWriter.write` from the decided fields the rule names, in the pattern of the summary pass:

1. **When.** `DerivedWriter.after_validation` (composed with the summary's in `tender.services.worker_jobs.tender_jobs`) queues `tender_derive` once no extraction or amendment map of the tender is under way; `DerivedGuard.after` queues it when a decision on a field a rule reads leaves none of them undecided. The pass writes nothing while a field a rule reads has a candidate and no decision (`write` returns None; `DerivedState.waiting_for` counts them): a table computed from half the decisions would be stale at once.
2. **Inputs.** `DerivedWriter.inputs`: for every field a rule names, the value that stands (the reviewer's where they edited) with its located evidence (the reviewer's own where they gave it), read as the summary reads the record (`summary.decided_field_value`, `summary.reviewer_evidence`). A field set aside as not in the document is absent. A rule sees `Decided(path, label, value, spans, version_no)` per input and nothing else.
3. **Rules** (`tender/domain_packs/power/derivations/`): `source_eligibility` (nine rows, one per possible source; status from the clause naming the source, else from the one general non-RE clause with `basis = inherited` and a condition saying so, else `not_addressed` with `basis = none`; the stricter of two clauses stands; storage from `storage_mandatory`, `storage_permitted` and `bess_charging_rule`; the technology of a linked build obligation is `required`) and `optimizer_constraints` (typed rows: `quantity` with comparator, value, unit and period; `temporal` with a date or an offset from an event; `obligation` that holds; each with `subject`, `source` where one applies, `basis`, `derived_from` and `clause`). Every row carries the page and quote of the span behind it (`clause_of`: the input's span that mentions the row's subject, else its first). Nothing is filled from the tender type.
4. **Stored as a candidate.** `ExtractService.record_candidate` in a run of `mode = "derived"` (`DERIVED_MODE`; `RECORD_MODES` groups it with the summary's `record` mode wherever "written from the record" matters), confidence 1.0, `llm_call_log_id` null, evidence spans copies of the inputs' spans, `prompt_name = derive`, `prompt_version` the rule module's `VERSION`; the earlier table is superseded; then `job(validate)`. The `structured_numbers_quoted` run rule exempts a derived run (its numbers are decided values, a few computed from them). A table with no clause behind any row is stored `not_found` with its rows and no evidence (`unsupported_candidate`): shown with that reason and not approvable, the treatment of a candidate whose value could not be located (the invariant's second case), not a reviewable candidate without evidence (its first case, which `_add_candidate` refuses). The candidate's rationale names the rule and version, the inputs, and the inputs' hash (`Inputs sha256:`), by which `DerivedState.current` knows the table in review is the reading of the record as it stands.
5. **Decided like any field, after the fields it reads** (`DerivedGuard`, handed to `ApprovalService` beside `SummaryGuard`; `DerivedState` served as `derived` in `GET /tenders/{id}/review`). Approve, edit and set aside are all refused while an input is undecided, while the table in review is not the reading of the record as it stands (`DerivedState.current`), or while it is being written again (`being_written`); a new decision on an input flags the table's decision with the reason (a `flagged` approval under the reviewer whose decision caused it; their earlier rows are not changed) and queues the pass. Only the approved table becomes canonical.
6. **On screen.** `web/src/review/RecordView` reads the `basis` key of a derived row: a row read off a general clause is drawn dashed and tinted with the label "Derived from a general clause, not one naming this source"; a row with no clause is dotted and grey, "No clause: not addressed"; a stated row looks like any record. The clause of each row is a key of the row; the inherited spans are the card's evidence chips.

The producer tag is `DERIVED <rule module> <version> from <input paths>` in FIELD-TRACE (`scripts/gen_field_trace.py`), beside `LLM`, `RULE`, `HUMAN` and `AGENT`.

## Model input profile: a typed projection for the financial model (designed 2026-10-05; the structured fields are built, the profile is not)

The canonical record feeds a financial model builder. A model computes with numbers, so the record must hold them as typed values, and the model must know for every input where it came from. Two things follow: structured fields in the schemas (below, "Structured siblings"), and a projection that turns canonical facts into model parameters.

**What it is.** `model_input_profile` is a read model over `canonical_fact`, one definition per tender type and model type. It stores nothing and writes nothing: the same facts, assumptions and profile version always give the same output. It reads approved facts only, never a candidate. It never invents a value.

**Where it lives.** The definition is data in the pack (`tender/domain_packs/power/model_profiles/<tender_type>.yaml`); the reader is `tender/services/model_profile.py`; the route is `GET /api/v1/tenders/{id}/model-inputs?model_type=...`. `core/` knows nothing of it. `model_tender(tender_id, model_type)` takes its inputs from the profile and from nowhere else.

| Tender types | Model type | Engine |
|---|---|---|
| solar, wind, hybrid, fdre, bess, generation, ipp | `power_project_finance` | planned |
| epc | `epc_contract_cashflow` | future work; the profile can be defined before the engine exists |
| transmission | `transmission_annual_charges` | future work, likewise |

**A profile definition** lists parameters. Each has a name, a value type and unit, and one source:

- `fact`: a canonical field path, and for a structured field the key inside it (`sector.power.fdre.demand_profile_structured#peak_availability_pct`).
- `derived`: a named pure function over other parameters of the profile (EMD in rupees for a stated configuration from the per-component rates; storage hours from MWh and MW). A derived value is `from_tender` only if all its operands are; it lists them, and its evidence is theirs.
- `assumption`: a key of `model_assumption` (per user and tender; capex, O&M, debt terms, and the bidder's own choices such as declared CUF or the solar, wind and storage split).
- optionally a `default`: a value with a written rationale and its source. Only parameters that are modelling conventions may have one. A parameter the tender is expected to state (a guarantee, a penalty, a tenure) has none.

**What it returns.** One entry per parameter, always, in the same order:

```
{ parameter, value_type, unit,
  status: present | absent,
  absent_reason: tender_silent | not_reviewed | not_applicable | left_to_bidder | null,
  value,                      # null when absent; never 0 as a stand-in
  provenance: from_tender | user_assumed | defaulted | null,
  from_tender:  { canonical_fact_id, field_path, key, tender_version, evidence: [{document, page, quote}], derived_by, operands },
  user_assumed: { model_assumption_id, entered_by, entered_at },
  defaulted:    { flag: true, rationale, source } }
```

Rules:

1. **Absent is not zero.** A field approved as "not in document" gives `absent` with `tender_silent`. A field with no decision gives `absent` with `not_reviewed`. A parameter the tender leaves to the bidder (peak hours chosen later by the buying entity) gives `left_to_bidder`. The engine must refuse to run, or ask, when a parameter it needs is absent; it may not substitute a number of its own.
2. **A value the tender states is a fact and cannot be overridden.** This is a fixed rule of the design (decided by the owner on 2026-10-05) and is not to be relaxed: the profile has no override, no precedence setting and no parameter by which an assumption or a default takes the place of a `from_tender` value. An assumption fills only what the tender leaves open. A different number for something the tender fixes is a scenario in the engine: it carries its own label, is shown beside the tender's value, and is never written back to the profile, to `model_assumption` as a replacement, or to the record. A test of the profile reader must show that an assumption given for a parameter the tender states is refused.
3. **A default is always visible.** `defaulted` carries its flag and rationale into every output of the model that depends on it.
4. **Units are fixed per parameter** (INR, MW, MWh, percent as 0 to 100, hours, months, INR per kWh). Conversions are named functions in the profile reader, each tested.
5. **Versions.** The profile is computed over the tender's current view (facts of the latest version that states them) and names the tender version of every fact, the schema version and the profile version.
6. **A test like FIELD-TRACE**: every `fact` source must name a field path and key that exists in the compiled schema of that tender type, and every structured key of a schema must be read by a profile or be listed as not used by any model.

### Structured siblings

A prose field that holds numbers has a structured sibling: a second field with path `<prose path>_structured` (or a named list: `shortfall_rules`, `cuf_terms`), of value type `record` or a typed `record_list`, whose keys each have their own type, unit and bounds (`KeyDef` in `core/schemas/model.py`; `keys:` in the pack YAML; one level of list inside a record). The prose field stays: it is what a person reads and what the summary is written from (the summary does not read structured fields).

Built on 2026-10-05, schema `v2`: 15 structured fields and one retyped list. Every type has `core.guarantees.emd_structured`, `core.guarantees.pbg_structured`, `core.commercial.payment_security_structured`, `core.penalties.delay_ld_structured`, `core.penalties.shortfall_rules` and `sector.power.common.deemed_generation_structured`. By type: fdre `demand_profile_structured`, `excess_energy_structured`; solar, wind and hybrid `cuf_terms`, `excess_energy_structured` (a field belongs to one section, so these are paths of the type, not of `common`); bess `degradation_and_augmentation_structured`, `soc_constraints_structured`; epc `milestone_payment_structured`, `ld_performance_structured`; transmission `element_wise_cod_structured`, `spv_acquisition_structured`, and `elements` with `kv` and `route_km` as numbers.

**How a record is written by the model.** As a list of strings, one `key: value` per stated key; a list inside a record once per item (`peak_blocks: window_start=05:00; window_end=10:00; hours=2`); a list of records one string per item (`key: value | key: value`). The answer's JSON schema therefore does not grow with the fields, the shared-window answer (`SharedAnswer`) is unchanged, and no grammar can be refused for size. `tender/domain_packs/core/value_types.py` turns the lines into the record: every key present, each in its type or null. A record with no stated key is refused: the value must be null.

**Schema version.** The packs are `version: v2` with `reads_versions: [v1]`: `v2` adds fields to `v1` and retypes one list (transmission `elements`, whose section was read again), so the registry also answers for `v1` with the `v2` schema and the runs of the sections that were not read again stay valid. The review state reads them together: `ReviewStateService.for_object` takes the runs of every version that `SchemaRegistry.versions_read_as` gives for the newest run's schema, which are the versions registered with the same groups, fields and rules. A version that changes or removes a field has other content, is not in that set, and is read on its own. The ten sections that gained fields have prompt `v2`.

**Compatibility of versions, checked when the packs are loaded** (`verify_versions` in `tender/services/packs.py`; the API, the worker and every command load the packs, so a fault stops them from starting and fails the test run):

- A version that reads an earlier one is compared with `released/<earlier>.yaml` field by field, for every tender type. A field of the earlier version that is missing fails the load: its candidates would be orphaned. A field defined differently (type, unit, allowed values, item keys, record keys) fails the load unless the pack lists it under `read_again` for that version.
- A field under `read_again` has its section read again under the new version, and its candidates from runs of the earlier version are not read: the registry holds them as excluded (`SchemaRegistry.exclude_fields`) and `ReviewStateService.for_object` leaves them out. `v2` lists one, `sector.power.transmission.elements`.
- A listed field that did not change, a listed version that is not read, and an earlier version without a released file also fail the load.
- A released version is frozen: once `released/<version>.yaml` exists, the loader refuses the version if any field has been added, removed or changed since. `v1` was released from the pack files of the last `v1` commit; `v2` was released when its fields were final and before any review.
- Labels, help text, bounds, the section and whether a field is required are not part of the comparison: they may change without a stored value meaning something else.

- **Extracted directly, in the same call as its prose parent** (same section group, same pages), with its own quotes. The reviewer decides it as its own field, so the gold set measures it by key.
- **Never derived by a model from the prose.** What is derived is derived by code in the profile, from structured keys, and points at their evidence.
- **A key the document does not state is null**, and the record says so key by key; a null key is `tender_silent` in the profile.
- **Two checks that cost nothing** (`tender/domain_packs/core/structured.py`). `structured_numbers_quoted` (a run rule): every number of a structured value must be printed in one of that candidate's own quotes; digits are compared after removing separators, lakh, crore and paise are also read in rupees, and numbers in words up to ninety-nine and "and a half" are read. A limit whose unit is "percent of declared CUF" may be printed as its distance from 100 ("+10%" for 110), and a plain decimal (a multiple, a count of months) as a percentage ("50%" for 0.5). `structured_agrees_with_scalar` and `power_structured_agrees_with_scalar` (cross-field rules): a key and the scalar field that holds the same fact must be equal; one stated without the other fails too. A value that fails either is `needs_review` with the key named. `python -m scripts.ingest_tenders revalidate` runs the checks again on finished runs.

On the reviewer screen a record is a card of labelled values with units, every key shown and "not stated" where the document is silent (`web/src/review/RecordView.tsx`); an edit has one input per key and sends the record. Accuracy by key (2026-10-12): the runner scores a record key by key (`match_record`, `FieldScore.key_outcomes`) and `summarise` adds the outcomes up per field and key (`Summary.by_key`, an item of a list under its key name); the reliability report has the section "Structured fields by key" and the dashboard the table of the same name.

## Reviewer screen (Stage 3)

`/review/<token>` opens straight into the tender; there is no list page. `web/src/review/ReviewApp.tsx` stores the token as a cookie (for the files the browser fetches itself), asks `GET /review-session` and `GET /tenders/{id}/review`, and shows the API's own sentence when the link cannot be used. Every call goes through `web/src/api/client.ts` with the token in `X-Review-Token`.

- **Left pane, 44%** (`SectionList`, `FieldCard`): the sections in review order, collapsible, each with decided/total; one card per field with label, help on hover, the value formatted by type (`lib/format.ts`: 12 Mar 2026, ₹ 25 lakh/MW, 19.0%), a confidence pill (green from 0.8, amber from 0.5, red below), failed rules as a red line and warnings in amber, one "p. 47" chip per evidence span (dashed with a question mark when the quote was not located), the model's rationale, a "v2 amendment" tag when the value comes from a later version, and what earlier versions said.
- **Right pane, 56%** (`PdfPane`): every page laid out at once from `GET /documents/{id}/pages` (sizes), each showing its pre-rendered PNG from `/files/renders/...` (lazy; the first two eagerly), so the first page is on screen before pdf.js has loaded. pdf.js (`pdfText.ts`, loaded on demand) reads the PDF by range requests from `/files/documents/...` and lays the selectable text layer over the pages in view; a page without a render is drawn by pdf.js. Search (`GET /documents/{id}/search`, hits marked on the pages), contents from the section map, a strip of page thumbnails, zoom, and a selector for the versions and their documents. The divider between the panes is draggable.
- **Evidence**: clicking a chip, or focusing a field, scrolls the PDF to the page (switching document when the evidence is in another one), marks the box of the quoted text, and pulses it; the focused field's evidence stays marked. A quote that was not located outlines its page.
- **Actions** (`ReviewScreen.decide`): Approve, Edit, Not in document and Flag each send `POST /approvals` at once, with the candidate and the decision it replaces; nothing is kept as a draft. The card shows "Saved" or the reason it was not saved; a stale decision (409) reloads the review. Edit opens an input typed to the field (date picker, number with unit, yes/no, dropdown, text) and takes the page and the words that state the value, required when the candidate has no located evidence; "Use text selected in the PDF" fills them from a selection in the right pane. Approve is not offered for a value without located evidence. "Add a note" (`DecisionNote`, 2026-10-12) opens a box whose text goes with the next Approve or Not in document as `approval.note` (the owner's feedback of 2026-10-06: a remark that keeps the value and is not a correction); the decision line shows it after the reviewer's name.
- **Keys** (`lib/keyboard.ts`): Enter approves and moves to the next undecided field, E edits, N marks not in document, F flags, J and K move, Escape cancels. Keys do nothing while typing in an input.
- **Complete review**: enabled once no required field is undecided; asks once, then `POST /tenders/{id}/complete-review`, and shows the summary at `/review/<token>/summary` with Download JSON. The link then opens the review read-only.
- **Orientation** (`GuidePanel`, text in `guide.ts`): a panel under the header, open on the first visit and afterwards as the reviewer left it (browser storage): what the review is for, how to decide a field, what the confidence figure means, the keys. `docs/REVIEWER-GUIDE.md` says the same outside the app; a unit test fails when the guide lacks a sentence of the panel.
- **Reading aids**: the confidence figure carries the caption "model confidence" and a hover text that says a low figure often means an ambiguous or partial statement in the document, with an example; the model's rationale is shown in full for the focused field and can be opened on any card; a section header counts its undecided fields that a rule flagged or that have confidence under 0.5 ("3 need a closer look"); the header shows how many fields are left and, after five decisions in a sitting, the time left at the reviewer's own pace (`lib/pace.ts`, the median gap between decisions).
- **Numbered evidence**: a field with several evidence spans numbers its chips (`evidence_span.ordinal`). A text whose sentences end in numbers (the summary) has no chips: each number is a small button that names its field and quote on hover and, clicked, opens the passage and spells both out under the text. A text without numbers lists, for the focused field, the words each chip quotes. In the PDF only the passage of the chip being shown is highlighted; the field's other passages are drawn faintly.
- **One light design in any system theme**: `index.css` declares `color-scheme: light` and gives inputs their own surface and text colour. Only pdf.js's text-layer rules are included, not its whole viewer stylesheet, which declared `light dark` for the page and gave inputs a dark surface under dark text in a dark system theme. The browser suite checks the contrast of every input and of the values in both themes.
- There is no bulk approve, no approve-all for a section and no timed auto-advance.

## Amendment review screen (2026-10-12)

`/review/<token>/amendments` (`web/src/review/AmendmentsPage.tsx`) is the second screen of a review link, offered in the review header as "Amendments · N fields · k to decide" when the tender has a later version. It reads `GET /api/v1/tenders/{id}/amendments` (`tender.services.amendments.tender_amendments`), a projection of the same review read model as the review screen: for every version after the original, the fields that version states (its entry in `ReviewField.entries`), each against what stood before it (the latest earlier entry's value as the reviewer left it, with their decision if any), typed `added` (nothing stood before), `changed` (the coerced values differ) or `restated` (the same value), with that version's candidate, evidence and decision, and whether that reading is the one the review decides the field on (`is_current`; false once it is set aside, or when a later version states the field again). The version header carries its kind and issue date, its documents (click to show one on the right), the sections its documents were read for (the routing's union, from the runs) and the `summary_of_change` given at upload. The summary field and the derived tables are left out: neither is something an amendment states. Fields no later version touches are counted as `untouched`.

The left pane lists the changes under their version, each as an `AmendmentCard` ("Before · v1 original" beside "This version · v2 amendment", the change kind, confidence, failed rules, evidence chips, the model's reasons); the right pane is the same `PdfPane`, opened on the first amending document. Decisions are the review screen's decisions on the same candidate through `POST /approvals` (Approve, Edit with the same `EditForm`, "Not in this version", Flag, Clear decision); setting a version's reading aside brings the earlier reading back on both screens, as `tender_review._current` already did. The page reloads its data after each decision; a completed review shows it read-only. The reviewer's keys work as on the review screen (Enter approves and moves to the next undecided change, E, N, F, U, J, K).

**What a change means (2026-10-15, `ChangeDetail`).** Under the two readings of a `changed` field: for a numeric type, "12 years → 15 years (+3 (+25%))" (`lib/diff.numericDelta`); for a text that is not a record, a word-level diff of the earlier reading against this one (`lib/diff.wordDiff`, a longest common subsequence over words, shown only while the two share more than a fifth of their words, since a diff of two unrelated texts is noise); and the impact cues the API carries on each change: `changes_decided` (what stood before is the reviewer's own approved or edited value, so deciding this reading replaces a canonical fact), `required`, and `impacts` (the derived tables whose rules read the field, from `derived_rules`: they are written again from it). The worked example is `seci-cfd-i` v5: the CfDA tenure 12 → 15 years is a required optimiser input that replaces an approved value.

**A provision withdrawn by a version (2026-10-15).** The owner's rule: "withdrawn by amendment" is a state of its own, distinct from "not stated" and from null, everywhere a value is held or shown. The model returns it under `extract/v2` (`withdrawn: true`, value null, the removing words quoted); `ExtractService` stores it as a candidate with `withdrawn`, value None and the evidence located like any value (a withdrawal without located words is rejected, as a value without evidence is); `tender.services.review` lets a later version's withdrawn reading take part like a value, so it is the entry to decide; `CandidateView.withdrawn` carries it to the screen. Approving it (`ApprovalService.approve`) is the decision that the provision no longer applies: no value is carried, the removing words must be located, and the canonical fact gets `withdrawn`; an edit with a value says the provision stands after all. The current view projects the withdrawal (above); the amendment screen lists it as `ChangeKind` `removed` (`AmendmentVersion.removed`) against what stood before; a derived table whose rule reads a withdrawn field carries it as a typed row — the optimiser table's `kind: withdrawn` under the subject the field would have constrained (rule v3, `SUBJECT_OF_INPUT`), the source table's `status: withdrawn` for the sources the field spoke of (rule v2, `SOURCES_OF_INPUT`), each with "withdrawn by vN" and the removing words as its clause (`Decided.withdrawn`/`withdrawn_by` from `DerivedWriter.inputs`; the rationale names them too) — instead of treating it as an absence. On screen: `FieldCard` shows "Withdrawn by this version" with what stood before struck through and offers "Approve removal" (decision line "Removal approved") — only while no edit has given the provision a value (`removal`); `AmendmentCard` shows the kind Removed; `SummaryPage` shows "Withdrawn by vN" with the removed value struck through; `model.approveBlocker` lets a located withdrawal through. Worked case: SECI CfD-I clause 40.3, the INR 5.80/kWh tariff ceiling deleted by Amendment-03 (v5); the owner approves the removal on the review link.

`docs/FIELD-TRACE.md` is generated by `make trace` (`scripts/gen_field_trace.py`) from the compiled schemas, the API's OpenAPI document, the ORM models, the prompt files, the rule functions and the web sources: one row per field path in review order. The `field_trace` check of the watcher regenerates it and fails when the committed file differs, or when a field has no UI component for its value type, no route or no column.

## Independent agent pass (Stage 5A)

A second model, from a different family than the extraction model, reads a tender on its own and submits one finding per field. It is not confirmatory: it sees neither the engine's candidates nor the gold values nor a reviewer's decisions, and its findings never become candidates or facts. Stage 5B compares the three readings per field.

**What it receives** (`agent/inputs.py`, `build_inputs`): the tender type; every document of the tender's versions up to the version the pass is run at, numbered from 1 in version order, each with its filename, version and role, its section headings, and the pages the section map names — the engine's own page selection, `core.services.extract.select_pages` run on the document's `section` rows and each readable group's routing hints, so the agent starts where the engine starts; and the fields, section by section (path, type, unit, required, label, help text, allowed values, record keys, the section's guidance), for every group read from pages — the summary field left out (it is written from the record, not read) and the derived sections left out (no model writes them). `describe` renders this as the brief that follows the instructions. The instructions are the registered prompt `core/llm/prompts/agent_pass/v1.md`; `agent_run.prompt_name/prompt_version` record it, like a candidate records its prompt.

**The three tools** (`agent/harness.py`, `Harness`; the SDK sees them through `sdk_tools`):

- `read_pages(document_no, page_nos, images)` returns the text of each page as the parser stored it (`page.text`), and the page's 150 dpi render as an image when `images` is asked for or when the page has no text layer (`agent_page_images` turns images off altogether). At most `agent_max_pages_per_read` pages per call (the rest are named back for a second call). Every page returned is marked read; `agent_run.pages_read` is updated as it goes. Any page of any document may be read, not only the named ones.
- `search_text(query, document_no)` finds the pages on which a phrase occurs, case-insensitive, with a snippet each, over every page of every document (or of one), up to twenty hits. Searching does not count as reading.
- `submit_finding(field_path, value, confidence, rationale, evidence)` is judged before it is kept. The value comes as JSON text and is coerced by the field's value type (`SchemaRegistry.value_types.coerce`, the same code the extractor's answers go through). The harness refuses, with a sentence the agent gets back and may act on: an unknown field path; a confidence outside 0 to 1; an empty rationale; a quote on a page that does not exist; a quote on a page the agent has not read; a quote that `core.evidence.locate` cannot find on the cited page (the cited page only — no adjacent-page or window fallback as in extraction, since the brief's rule is "not found on the cited page"); a value with no evidence; a value the field's type refuses. A null value with no evidence is recorded as `not_found` (the explicit abstention the instructions ask for); a null value with located evidence as `withdrawn` (the removing words). A rejected attempt is kept as a finding of status `rejected` with its `reason` and the quote as cited (located fields null), so the comparison can see what the agent tried. A later accepted, not-found or withdrawn finding for a field supersedes the earlier one (status `superseded`, audited). Each attempt is one row with its `ordinal`.

**The run** (`agent/service.py`, `AgentPassService`): `start` checks the inputs now (a superseded tender, a tender without a version, an unparsed or unmapped document are refused here), writes `agent_run` as `queued` with `pages_offered` and the documents by number, audits it, and queues an `agent_pass` job. The agent container (`agent/main.py`, `AgentWorker`) claims that job kind and nothing else, and `run` builds the inputs again, marks the run `running`, and hands the harness, the instructions and the brief to a driver. The real driver (`sdk_driver`) builds an `Agent` with the three tools, runs `Runner.run_sync` for at most `agent_max_turns` turns with parallel tool calls allowed (several findings from one page cost one model call; the harness lock serialises them) and tracing disabled (nothing leaves to the SDK's trace endpoint), through a `RunConfig` whose model provider is `LoggedProvider`: the OpenAI Responses-API model wrapped in `LoggedModel`. Tests hand in a scripted driver instead. `finish` closes the run: `done` when the loop ended (with a note naming any field left without a finding), `stopped` at the turn limit or on a model error after some turns (the findings made so far stand), `failed` when the inputs could not be built; turns, `tokens_in`, `tokens_cached`, `tokens_out` and `cost_usd` are the sums of the run's `llm_call_log` rows, so the run's cost is what its logged calls say. The settings: `openai_model`, `openai_price_in_per_mtok`, `openai_price_out_per_mtok`, `openai_cache_read_factor` (the factor on the input price for tokens the provider served from its prompt cache), `agent_max_turns`, `agent_max_pages_per_read`, `agent_page_images`. Prices are list prices set in `.env`; the invoice is the truth.

The `openai-agents` package is the one SDK `agent/` uses; the only module that touches OpenAI is `core/llm/agent_calls.py` (operating rule 8).

## Three-way comparison (Stage 5B)

`evals/threeway.py` puts three readings of every gold field side by side: the reviewer's (the gold record, at the version it was reviewed), the engine's (the candidate in review for that field at that version, `evals.runner.candidates_in_review`, the same reading `make eval` scores) and the agent's (the standing finding — `accepted`, `not_found` or `withdrawn` — of the latest `done` or `stopped` agent pass over the tender **at the gold record's reviewed version**, so the agent read the documents the reviewer saw and no later ones). Engine and agent are each scored against the reviewer with the scorer's own rules (`evals.runner.score_field`: the same tolerances, the same coercion), so the comparison is fair to neither. A gold tender without a finished pass at that version is named in the summary and left out, never counted as abstentions.

Each decided field falls into one of six classes:

- `all_agree` — engine and agent both match the reviewer (a value, or an abstention where the reviewer marked the field absent).
- `engine_right_agent_wrong`, `agent_right_engine_wrong` — one reading matches, the other does not.
- `both_wrong_same_way` — both miss and their two values match each other (by the scorer's rules).
- `both_wrong_differently` — both miss, each in its own way.
- `both_abstained` — the reviewer found a value, neither model returned one.

Long-text fields are `needs_judgement`, outside the six (the scorer leaves them to a human), and are counted apart.

`THREEWAY-REPORT.md` (`make threeway`, `POST /api/v1/admin/threeway`; rewritten on every run) gives the counts by class, by tender type, by agency and by field, and four lists that say what each pattern asks for: *both wrong the same way* — the schema or the document (an ambiguous clause, a table against a clause, a definition that does not fit); *the models disagree* (one right, or both wrong apart) — the field earns a mandatory second reading in production before it is shown; *the agent caught what the engine missed* — the agent's path to the evidence (its search, the page it cited) is what to fold into that section's extract prompt, then `make eval PROMPT=<section>/vN`; *both abstained* — routing, a scanned page, or a clause in words the prompts do not expect.

**The production confidence rule.** Per field, over every gold instance that is not `needs_judgement`, the share in `all_agree`. A field is "auto-surface with low-review" only when that share is at least `AGREEMENT_MIN` (0.97) over at least `INSTANCES_MIN` (15) instances; otherwise it stays full review. The rule and every field's figures are written to `evals/results/review-emphasis-<tenant>.json` and printed in the report. The reviewer screen reads the file (`ReviewField.emphasis`, `"full"` or `"low"`, from `settings.results_root`) and a `low` field gets a quiet badge on its card — its default look and nothing more. No auto-approval exists: the truth pipeline, the approval handler and the review counts are untouched by the emphasis.

## Identity, tenancy and the two products (Stage 5C)

**Principals.** A request acts as one of four principals (`core.services.identity.Principal`), resolved by `api/middleware/auth.py` in this order and stopped at the first that fits: a review token (header or cookie, as in Stage 3: the token's reviewer, limited to the review routes of its tender — `review_token._admit` and `ALLOWED` are what judge it); a session cookie `tie_session` (a signed-in user: `app_user` with its role and tenant); a Bearer API key `tie_live_…` (an `api_client` with its scopes); the `X-Admin-Token` header (internal automation and the tests, admin in the configured tenant). A request through the public proxy with none of these is refused `review_link_required` with the sentence "Sign in, or open the review link you were sent", except `/health` and the sign-in routes; a stale session is `session_expired`, an unknown or revoked key `api_key_invalid`, a sign-in the settings do not admit `login_refused`. `api.deps.PrincipalDep` hands the principal to a route, and `get_session` scopes the request session to its tenant (`set_tenant`). A principal carries its own tenant and the tenants it may read: its own, and `public` (Stage 5D).

**Roles** (`auth._allowed`). `reviewer`: `GET` on the tender, document, schema, review and published routes of the tenant, plus `POST /approvals` and `POST /tenders/{id}/complete-review`; `approver`: the same plus `POST /admin/gold`; `api_client`: the `GET` intelligence routes (`/tenders`, `/published`, `/published.pdf`, `/changes`, `/compare`, `/reliability`) and, with the `model` scope, `POST /tenders/{id}/model`, never a write to a field; `/admin/*`: an admin's session or the admin token. A principal outside a route's roles is refused.

**Sign-in** (`core/services/oidc.py`: `OidcProvider`, `GoogleOidc`). Google OIDC (`OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, `OIDC_ISSUER`): `GET /auth/login` sends the browser to Google with a signed state (`SESSION_SECRET`); `GET /auth/callback` exchanges the code, verifies the id token against Google's published keys (PyJWT with `PyJWKClient`: RS256, issuer, audience, expiry), admits only a verified address of `OIDC_ALLOWED_DOMAINS`, finds the user by subject or makes one with `OIDC_DEFAULT_ROLE` (`admin` for `BOOTSTRAP_ADMIN_EMAILS`), and sets the `tie_session` cookie (HttpOnly, Secure, SameSite=Lax, `SESSION_HOURS`); `POST /auth/logout` revokes the session, `GET /auth/me` says who the request is. A session is a `login_session` row with the hash of a random token: revocable at sign-out or by an admin, and audited (`IdentityService`). With the settings empty, sign-in is refused with a plain sentence — the VM today. Tests use a scripted provider (`tests/fixtures/oidc.py`).

**API keys and metering.** A key is made by an admin (`POST /admin/api-keys`), shown once, stored as a sha256 hash with the prefix the holder recognises it by. Each call it makes — and each call a signed-in user makes on the intelligence routes — writes a `usage_record` whose `tenant_id` is the **calling** tenant, never the resource's (or free-tier limits could not be enforced), with the route, the tier, units and tokens; `GET /admin/usage` sums them. The rate limit per minute and the daily cap are counts over that table (`API_KEY_RATE_LIMIT_PER_MIN`, `API_KEY_DAILY_CAP`, or the key's own); over either, `429 rate_limited`.

**Tenancy.** Row-level security (see the data model) is the isolation: the request session is scoped to the principal's tenant before the first statement, every table with a `tenant_id` is under `FORCE` policies, and the app's own role has no ownership to switch them off. The service layer's tenant filters remain and are now a second line. The system scope `*` is used only inside the identity steps that must find a principal before its tenant is known.

**Two products from one core.** `PRODUCT=enterprise` (the default) mounts every router and is what the web front end calls; `PRODUCT=api` mounts `API_PRODUCT_ROUTERS` only — the document, tender, reliability and published routers, and of those only their `GET` routes (`API_PRODUCT_READ_ONLY`), plus the OpenAPI document — for API-key clients (`api.main.routers_for(product)`). The same image, the same code; a deployment chooses with one setting, and the Cloud Run picture runs one `api` service of each.

## Published view and publication state (Stage 5C)

`tender/services/published.py` (`GET /tenders/{id}/published`) is the client-facing reading of a tender: every field the schema names, from `canonical_fact` alone — the value, the version that set it, the evidence pages, the review date and the reviewer's **role** (never the name of an external reviewer, never a candidate). The values come through `current_view`, which reads `canonical_fact` only; the summary and the derived sections are left out (written from the record and from decisions, not read from the document). A field without a current fact is a typed gap, `not_reviewed`, with its reason (undecided, set aside as not in the document, withdrawn by a version) and the page the engine's reading cited as the likely place to look; never a blank or a null. The reviewer's role is read from `app_user` by email, else `reviewer` (a link holder). The response carries a reliability block (accuracy and n for the tender's type from the latest plain evaluation in `evals/results/`, `as_of`; "none" when there is none) and the sentence that the tender document is the authoritative source. `tests/tender/test_published.py` asserts that a candidate's value appears nowhere in the published output.

**Publication state** (`tender/services/publication.py`, `publication_state`), independent of the review state, after the Stage 5D rules decided on 2026-10-04: `published` — the current version is reviewed; `update_pending` — a later version exists and is not yet reviewed: the view stays, every response carries a banner naming the version and its issue date, and the fields that version touches (`fields_touched`: the fields its runs produced reviewable candidates for) are marked `possibly_superseded`; `publication_suspended` — the unreviewed version touches one of the thirteen `CRITICAL_FIELDS` (the bid submission deadline, total capacity in MW and MWh, EMD and PBG per MW, the tariff ceiling and SCOD months in both their common and `ipp` paths, minimum commissioned MW, net worth per MW, the turnover and liquidity requirements): the view answers the suspension and the amending document, not the stale values, and the tender leaves the library's search; `not_published` — no completed review yet. On approval of the new version a new snapshot is taken and the state returns to `published`.

`changelog.py` (`GET /tenders/{id}/changes`) lists, per version, the facts it set against what stood before, with the amending document and date; `compare.py` (`GET /tenders/compare?ids=`, at most six tenders, a suspended one left out) puts tenders side by side with provenance on every cell and `not_reviewed` cells marked; `published_pdf.py` (`GET /tenders/{id}/published.pdf`) writes the published view as a PDF with pymupdf, the same view giving the same text (only the file identifier the library writes differs between saves), with an appendix that lists every field's document and page.

## Public library tier and MCP (Stage 5D)

**Tenant and principals.** The library is the reserved tenant `public` (seeded by migration 0017, `plan = public`): the same rows, the same pipeline, the same review requirement as any tenant. A free account is a tenant of its own (`plan = free`, named `free-<hex>`) with no tenders and one user; sign-up (`POST /auth/signup`, Google OIDC as for the enterprise sign-in) makes both in the system scope. Every principal reads its own tenant and `public` (`read_tenants`, set on the request session as `app.read_tenants`); no end-user principal writes to `public` under any role — the database refuses it (`tests/core/test_rls.py`, the row-level policies of 0018), not only the service layer. Reviewer and ingestion service accounts are the only writers there: the management commands, scoped to `public`, ingest and extract a library tender exactly as an `ergplan` one. MCP clients authenticate through OAuth (`mcpserver/auth.py`: dynamic registration of public clients, the authorization-code flow with PKCE S256, a consent page shown to a signed-in user at `/api/v1/oauth/consent`, codes single-use and ten minutes long) and receive an access token that is an `api_key` row named `mcp:<client_id>`, scoped `public:read` (and `own:read` for an enterprise plan), tier `free`, so one credential model and one metering path serve keys and tokens alike; server-to-server credentials are issued in the enterprise product (`/admin/api-keys`), never at free sign-up. Usage is attributed to the calling tenant (`usage_record.tenant_id`), never the resource's, with `resource_tenant_id`, the user or key, the tool, the tier, tokens and the time; the free tier's rate limit and daily cap (`FREE_RATE_LIMIT_PER_MIN`, `FREE_DAILY_CAP`) are counts over it, and there is no bulk export.

**Tiers.** Free: `search_tenders`, `get_tender`, `get_field`, `get_document_page`, `find_matching_tender`, `list_changes`, `compare_tenders`, `reliability_report`, over `public` only. Paid (an enterprise tenant's user or key): the same over its own tenders, plus `model_tender`, `save_model_assumptions`, `my_watchlist` and the front end. Every public response carries the provenance and the reliability block a paid one carries, and the sentence that the tender document is the authoritative source.

**Publication, corrections and takedown.** The state machine of Stage 5C (`published`, `update_pending`, `publication_suspended`, `not_published`) is completed by holds: a `publication_hold` of kind `takedown` (an agency's or rights-holder's request, placed by an admin within one business day of its arrival — a process, recorded in `docs/KNOWN-GAPS.md` under "Takedowns" and in the audit log) or `correction` suspends publication whatever the review state until an admin lifts it. A correction case (`POST /public/corrections`: field path, the claimed error, the claimant's reasoning; from any signed-in user or key, or the public form) creates a `correction_case` and opens a review round scoped to the field for the tender's reviewer; it never changes a value. If the reviewer agrees, the new approval supersedes the old one through the normal pipeline, and the change is visible in `list_changes` with its date and reason; the case is then `accepted`, else `rejected`, with a resolution.

**The eleven tools** (`mcpserver/tools.py`; each calls the library services of `tender/services/library.py`, `corrections.py` and `finance.py`, so the API routes and the tools share one implementation). Their base definitions were never given in the master prompt (the owner's decision of 2026-10-04 left them unspecified); these are ours, written from the widget and tier text, and are the owner's to correct:

- `search_tenders(query?, tender_type?, agency?, state_filter?)` — published tenders of the caller's read tenants matching the words, with type, agency, capacity, bid deadline and state; a suspended tender is left out.
- `get_tender(tender)` — the published view: facts by section with value, unit, version tag, page chips, `not_reviewed` gaps with their reason; the publication banner; review date, reviewer role, reliability. Renders `tender_card`.
- `get_field(tender, field_path)` — one fact with its full provenance (version, evidence quotes and pages, review date, role) or its gap.
- `get_document_page(document_id, page_no, quote?)` — the page image's URL and the page's text, the quote located on it when given, so a chip can show the page with the quote highlighted; the URL is served by `/files` under the caller's credential.
- `find_matching_tender(title_or_number, agency?, capacity_mw?)` — the one reviewed tender a description names, or `no_match` with up to three candidates and their distinguishing attributes; never the nearest tender silently.
- `list_changes(tender)` — the changelog across versions. Renders `changes_view`.
- `compare_tenders(tenders)` — at most six, fields as rows, provenance per cell. Renders `comparison_table`.
- `reliability_report(tender_type?)` — accuracy per type and section with n and as-of, the stability bar.
- `model_tender(tender, model_type="power_project_finance", assumptions?)` — the tender-fixed parameters with provenance, the saved or given assumptions, the engine's figures; read-only. Renders `financial_model`. Paid.
- `save_model_assumptions(tender, assumptions, model_type=)` — persists the caller's assumptions and returns what was saved. Paid.
- `my_watchlist(add?, remove?)` — the followed tenders with bid deadlines and days remaining. Paid.

Each tool returns a `ToolResult(structured, text)`: structured content and a text fallback that is a complete answer on a host without MCP Apps (a test asserts it); `run_tool` guards the tier (`tier_required` for a paid tool asked by a free principal), counts the free limits (`FREE_RATE_LIMIT_PER_MIN` 20, `FREE_DAILY_CAP` 200) and writes a `usage_record` with tool `mcp:<name>` on the calling tenant.

**The widgets** (`mcp/widgets/`). Four single-file HTML resources served as `ui://widgets/<name>.html` with `text/html;profile=mcp-app`, named by the tool's `_meta.ui.resourceUri`; the server's `UiExtension` declares `io.modelcontextprotocol/ui`. The bridge, as the widgets speak it: `ui/initialize` (protocol 2026-01-26) answered by `ui/notifications/initialized`; the tool's result arrives under `ui/notifications/tool-result` (the widgets also accept `ui/notifications/tool-input` and `ui/tool-result`); outgoing calls go as `tools/call` and `ui/request-tool-call`; each widget also exposes `window.__render(data)`, which the jsdom tests and a host without the bridge can call. The rules: a widget renders only what its tool returned, declares and calls no outside host (the spec's CSP model; anything further is a bridge tool call); empty states are designed before the happy path — a `not_reviewed` field is a visibly marked gap with its reason and a link to the likely page, never a blank, a dash or a zero; every value shows its page chip, and the chip calls `get_document_page` through the bridge and shows the page with the quote highlighted; the reliability block sits in the footer; light and dark themes, readable at a chat column's width, usable on a phone. `tender_card` (sections collapsible, version tags, the banner when not published), `financial_model` (the tender's locked parameters with page chips on the left, the user's assumptions marked "assumed, not from the tender" on the right, the figures labelled indicative, a cashflow chart), `changes_view` (the version timeline, old to new with evidence), `comparison_table` (sortable, exported as CSV from the widget's own copy of the data).

**One financial engine.** `tender/services/finance.py` (`power_project_finance`) is the only calculator: it serves the widget's bridge call, the front end and `POST /tenders/{id}/model` alike. The widget may compute a provisional figure while a slider moves, shown as provisional, and replaces it with the server's when the debounced bridge call returns; anything saved, exported, quoted or shown as final comes from the server. A test asserts the widget and the server agree within a rounding tolerance over a fixture set of assumption combinations — a divergence is a bug in the widget, never a reason to change the engine. `model_tender` computes and returns; `save_model_assumptions` persists: no analytical tool changes state. Assumptions live in `model_assumption`, per user and tender, and are never canonical facts.

## Award results import (Stage 6)

The RE-tender-results dataset (`Ergplan/RE-tender-results`, read once from a clone at `/work/ref/RE-tender-results`, mounted read-only into the app containers) holds award results for the agencies' tenders: 623 records over 122 source publications, 116 of them PDFs archived with their sha256. Stage 6 brings them in as a reviewed object type beside the tenders, under the invariants unchanged: nothing from the dataset reaches a reader unreviewed.

- **Object.** One `award` per source publication, not per record: a result sheet or a CERC order is one review sitting, one table against one PDF. Its schema is the `result` pack's `result.award` (`tender/domain_packs/result/`): `procurer`, `reference`, `result_kind` (`auction_result`, `cerc_adoption_order`, `allocation`, `register`), `result_date`, and `winners`, a `record_list` keyed bidder, allocation, capacity and unit, price and unit, adopted capacity and price, status, notes. The pack compiles through the same catalog as the tender packs (`object_type: award`, `namespace: result`; field paths `result.award.<field>`); its one section is `imported`, which the extractor never reads and the trace tags IMPORT. The dataset's verification tier and the file's hash are provenance on the `award` row, not fields: a field needs located evidence on the page, and the page states neither.
- **Source admissibility.** `infra/source-domains.yaml` is the committed allowlist (DECISIONS 2026-10-07); `SourceAllowlist.admissible` accepts a listed domain and its subdomains over any scheme and nothing else. The importer lists every host of the run first and stops before writing anything when one is not admissible; the owner adds the domain or leaves the source out.
- **Importer.** `ResultsImporter.run` per PDF source: the file's sha256 must equal the dataset's (stop on the first mismatch); `IngestService.upload` with `source_url` and `retrieved_on` (deduplicated: a publication already imported is skipped); `ParseService.parse(map_sections=False)`, so the pages exist for evidence and nothing queues a model call; the `award` row; one `extraction_run` in mode `import` with `model = RE-tender-results@<commit>`; then the candidates through `ExtractService.import_candidate`, which locates each quote with core's resolver on the cited page (then its neighbours, as for a model's quote) and caps confidence at 0.8. The procurer is quoted by the agency's name as the page prints it, the reference by the RfS number (from the SECI research records, which keep what data.json drops) or the petition number, the kind by the words that show it, the date by its printed form; each winner row by its bidder and its price (its capacity when no price is given), the two quotes carrying the row's number as their ordinal. A quote that is not found leaves its span `unresolved`: the candidate is shown unlocated at capped confidence and cannot be approved without reviewer evidence, the invariant that already governs a model's reading. The six HTML registers are left out and counted, never converted.
- **Validation.** `ValidationService.validate` as for any run, with the pack's rules: every row has a status, a stated capacity is above zero, adopted ≤ awarded, a price lies in the band of its unit (and has one), the units fit the kind of publication; and the run rule `award_rows_located`, which names the rows whose bidder or number was not found (a number alone proves nothing). A failure sends the table to `needs_review` with the rule's name; nothing is hidden or dropped.
- **Tender link.** `award.tender_id` is set only by an exact match of the RfS number against `tender.external_ref` (`rfs_number`), or when a tender's number is found verbatim in the order's own page text (`page_text`, with the page). Never fuzzy. `GET /tenders/{id}/awards` gives a tender's publications with their approved rows only.
- **Review.** The reviewer opens an award link into the same split screen (`web/src/review/award.ts` shows the award through the tender's shape and points `review` and `complete` at the award routes); decisions go through `POST /approvals`; `complete-review` is refused while a required field (procurer, reference, kind, winners) has no decision, then marks the link completed and the award `reviewed`. No snapshot table: the award's facts are its canonical rows. `GET /awards/{id}/results` reads `canonical_fact` and nothing else.
- **Links.** `python -m scripts.review_token create --award <source id>` and `create-awards --reviewer <name> --out <file outside the repo>` mint the links; they are credentials and never enter the repository.

## Job chain

`worker.runner.Runner` claims one due job at a time (`core.services.jobs.claim_next`, `FOR UPDATE SKIP LOCKED`) and runs its handler. Since Stage 5A two processes share the job table, each claiming only the kinds it has a handler for (`claim_next(kinds=…)`): the worker its chain and the tender layer's kinds, the `agent` container `agent_pass` alone. `agent_pass` is queued by `POST /tenders/{id}/agent-pass` (`AgentPassService.start`) and runs the agent loop; it enqueues nothing. Each step of the chain enqueues the next:

`upload` → `parse` → `section_map` → `index_document` (Block 5: the document's retrieval chunks, replaced on every run; `embed_pending` embeds chunks written while the embedder was unavailable), and `start_run` → `extract` → `validate`. When the last run of a tender is validated: `tender_summary` → `validate` (the summary written from the record), and, for a later version of a `reviewed` tender, `tender.services.rounds.RoundOpener` opens a review round (no job of its own: a token and an audit row, in the validation's own hook). For an amending document of a tender: `amendment_plan` → `extract` → `validate` (the tender layer hands its job handlers to `worker.runner.Runner` as `extra_handlers`). Extraction of a tender version is started explicitly (`POST /tenders/{id}/extract` or `python -m scripts.ingest_tenders extract`) once its documents are parsed; it queues one `extract` job per document. Beside the chain, `source_freshness` (`tender.services.freshness`): the worker queues one when it starts and none is pending (`ensure_scheduled`), the job checks every tender's source page against the documents held, records each comparison in the audit log and queues the next check `FRESHNESS_INTERVAL_DAYS` later (7; 0 turns it off); `POST /admin/freshness` queues one on demand that does not repeat. It fetches pages and files to hash them and ingests nothing. Block 6 adds `tender_extract` (a submitted version: re-queued every 30 s until its documents are parsed and its type known, then `start_run`) and `webhook_deliver` (one job per delivery, retried by the deliverer's own schedule up to six attempts); `extraction_done` is emitted when `after_validation` reports the tender settled, `new_version` in `add_version`'s transaction, `review_complete` in `complete_review`, `amendment_detected` by the freshness check.

A failure is stored with its traceback in `job.last_error`. A retryable failure is retried three times with backoff (30 s, 60 s, 120 s; `max_attempts` is 4); a non-retryable one (unknown document, schema or prompt; a refusal, truncation or invalid output from the model) fails at once. When an extract or validate job fails for good, the run is marked `failed` with the error. Extraction commits per shared window and reads calls it has already paid for from the call log, so a retry resumes where it stopped. A batch run's `extract` job submits or collects a batch and queues the next `extract` job a minute later, until both waves are in. When the worker starts, jobs still marked `running` were left by a worker that died and are put back in the queue (`jobs.requeue_orphans`), for its own kinds only; the agent container does the same for `agent_pass` when it starts, so the two do not put each other's running jobs back. The newest finished run of an object keeps the live candidates: a run supersedes the candidates of runs started before it, and supersedes its own if a run started later has already finished. A section map that fails for good is shown in `document.error`. A worker serves one tenant (`TENANT_ID`): it claims, completes, fails and re-queues only that tenant's jobs.

```mermaid
  I[Internet] -- "Cloud Armor: allowlist from infra/allowlist.yaml" --> LB[HTTPS load balancer, URL map]
  LB -- "/" --> W[web: nginx, static bundle]
  LB -- "/api/*, /files/*, /health" --> A[api: PRODUCT=enterprise]
  LB -- "api host" --> B[api-product: PRODUCT=api]
  A --> SQL[(Cloud SQL Postgres 16, connector)]
  B --> SQL
  K[worker: min 1 instance, CPU always on] --> SQL
  G[agent: min 1 instance] --> SQL
  A --> GCS[(GCS bucket: documents, renders)]
  K --> GCS
  G --> GCS
  M[migrate: Cloud Run job, owner URL] --> SQL
  SM[Secret Manager: keys, DB passwords, OIDC client, session secret] -.-> A & B & K & G & M
```

`worker` and `agent` poll the job table, so they run with a minimum of one instance and CPU always allocated; `api` and `api-product` scale to zero. Files go through the storage interface to GCS (`STORAGE_BACKEND=gcs`, `GCS_BUCKET`) and are served by `GET /files/{path}` on the API, since no proxy has a disk there. The migrate job runs `alembic upgrade head` with the owner's URL before each release; the services connect as `tender_app` with its Cloud SQL password from Secret Manager. The runbook in `infra/cloudrun/README.md` lists, in ten steps, the `gcloud` commands that create the Artifact Registry repository, the Cloud SQL instance and database, the bucket, the secrets, the services (`service.api.yaml`, `service.api-product.yaml`, `service.worker.yaml`, `service.agent.yaml`, `service.web.yaml`) and the migrate job (`job.migrate.yaml`), the Cloud Armor policy from `infra/allowlist.yaml` and the load balancer; every one of them is the owner's step (`!` prefix), and `deploy.sh` (`--print-only`, `--only <service>`; images from `cloudbuild.python.yaml` and `cloudbuild.web.yaml`) is the release path once they exist. Three limits the runbook names: nothing on Cloud Run sets `X-Public-Request` unless the load balancer adds it (`--custom-request-header`, step of the runbook), `service.web.yaml` carries a `[HASH]` placeholder for the API upstream until the service exists, and the worker there has no `/work/tenders`, so the freshness check skips (KNOWN-GAPS). The cutover is: run the runbook; set the DNS name; register the Google OIDC client with the callback on that name; copy `/data` to the bucket and the database with `pg_dump`/`pg_restore`; then decide whether the VM keeps serving (KNOWN-GAPS).
